## 關於這個專案

**慕沐村 Mulage pet** 是為合作的寵物美容店獨立開發的全端管理系統，目前**每天實際用於營運**：顧客用 LINE 預約，店員用後台開單收款，店家用報表看業績。

開發背景：服務業第一線資歷 18 年，非本科出身，透過自學完成架構設計、後端開發、資料庫設計、第三方串接與正式環境部署。以下記錄的是開發過程中遇到的幾個實際問題，以及當時的分析與解法。

## 工程決策與問題排查（節選）

以下是專案中幾個具代表性的技術決策，記錄當時遇到的問題、考慮過的取捨，以及最後採用的做法。

### 1. 金流併發扣款的競態條件（Race Condition）

**問題**：原本的錢包扣款邏輯是「讀取餘額 → 比較 → 寫回」，在同一顧客短時間內觸發多筆請求時，可能出現餘額被超扣的風險。

**解法**：改用 `SELECT ... FOR UPDATE` 悲觀鎖重新讀取錢包列後才扣款，讓同一顧客的併發請求被序列化處理，從資料庫層級杜絕超扣。

### 2. 同時段預約超收

**問題**：店家規定同一時段最多接待固定數量的寵物，但「還不存在的預約列」沒有東西可以上鎖，光靠應用層判斷無法防止併發超賣。

**解法**：設計獨立的時段容量計數表（`SlotCapacity`），對「時段」本身加悲觀鎖，讓併發預約請求依序處理、即時回報剩餘名額。

### 3. 時段容量設定：週期範本與單日覆寫的分層設計

**問題**：店家反饋預約時間過於鬆散，希望能針對一天當中每個時段分別設定固定的預設可接組數（例如某時段固定接 4 組、下一個時段暫停、之後每個時段固定接 1 組），但同時仍需要能因應現場突發狀況（例如單一顧客一次帶多隻寵物）即時關閉後續時段。

**解法**：拆成兩層機制——一份通用的預設容量範本（不分星期幾），決定每個時段的預設上限；既有的單日容量計數表則保留作為即時覆寫用途，覆寫只影響當天、不回溯影響範本本身。範本值採 lazy 初始化寫法（第一次讀取時若不存在才建立預設列），而非透過資料庫遷移檔案寫入固定值，原因是這是店家會持續調整的營運設定，不是需要跨環境保持一致的固定資料。

### 4. 服務項目種子資料：從 `count()==0` 判斷到 Flyway

**問題**：服務項目的初始資料原本用 `count()==0` 判斷「只在全新資料庫時建立」，但正式站資料表早已不是空的，導致新增的種子資料實際上從未被種進正式環境，這個問題重複發生過。

**解法**：改用 Flyway 管理種子資料的新增與回填，schema 本身仍交由 Hibernate `ddl-auto=update` 處理；由於 Spring Boot 預設會讓 Flyway 在 Hibernate 建表之前執行，另外寫了一個 `ApplicationRunner` 手動控制執行順序，確保 Flyway 遷移一定在建表完成之後才跑。

### 5. Hibernate `ddl-auto=update` 的其他實務限制

專案未在 schema 本身導入額外遷移工具，純靠 Hibernate 自動建表，過程中歸納出幾條實務規範：新增 `NOT NULL` 欄位需搭配 `columnDefinition` 預設值，避免對既有資料的表格做 `ALTER TABLE` 時失敗；`ENUM` 型別改用 `VARCHAR` 儲存，因為 Hibernate 不會自動幫已存在的 ENUM 欄位擴充允許值清單。

### 6. LINE LIFF 多頁面路由的官方限制

**問題**：原本假設可用「單一 LIFF ID + Endpoint URL 路徑轉發」服務多個頁面，實測後行為不一致。

**解法**：查證 LINE 官方文件後確認 LIFF URL 的路徑會被包裝進 `liff.state` 查詢參數並不會真的轉發，改為「一個功能頁面對應一組獨立 LIFF App」的官方支援架構，目前共 9 個頁面各自獨立申請。

### 7. 前端錯誤訊息被靜默吞掉

**問題**：`fetch()` 呼叫後端 API 時，若錯誤回應是純文字而非 JSON，前端寫死用 `res.json()` 解析會拋出例外並被 `.catch()` 接住，導致看不到真正的失敗原因。

**解法**：統一後端錯誤回應格式為 JSON；前端改為先讀 `res.text()`，能解析成 JSON 才當 JSON 用。

### 8. 例外處理統一：從散落的 try/catch 到分業務例外類別

**問題**：13 個 REST controller 各自用 try/catch 把例外組成 `Map.of(...)` 回傳，共 33 處重複樣板，格式不一、也沒有型別保護。

**解法**：建立 `BusinessException` 為基底、依業務拆分的例外類別（預約、付款、績效、錢包、會員、庫存等），交由全域例外處理器統一轉成 `ErrorResponse` DTO。之後逐支 Service 遷移（`AppointmentService` 78 處、`WalkInOrderService` 53 處等），順便清掉已失效的死碼 try/catch。

### 9. N+1 查詢與零售商品超賣

**問題**：後台預約列表與 Dashboard 對每筆預約各自觸發多次延遲載入查詢，資料一多就變成數百條 SQL；零售商品庫存扣減則與錢包有同樣的「讀取→比較→寫回」競態風險。

**解法**：預約查詢改用 `JOIN FETCH` 一次帶出使用者與服務項目，其餘關聯改為批次查詢；零售商品扣庫存比照錢包加上悲觀鎖，避免同一商品被同時賣超。

### 10. 會員自助認領的安全邊界

**問題**：老客戶以電話號碼認領店家匯入的既有資料，若只憑電話即可認領，任何人輸入他人電話就能取得對方的會員資料與儲值金。

**解法**：新客報到改為先輸入電話分流——查到既有會員時，必須再以毛孩名字或姓名確認才能認領；查詢與認領各自限制次數（10 分鐘內 5 次）；填寫新會員資料時擋下屬於未認領會員的電話，避免繞過驗證。認領時會員卡與等級一併過戶。

### 11. 正式站監控：依賴套件命名的陷阱

**問題**：導入 Sentry 後部署完全沒有相關啟動 log，代表自動設定根本沒載入。

**解法**：查證官方文件後發現 Spring Boot 4 對應的模組是 `sentry-spring-boot-4`，而非沿用 Boot 2/3 慣例的 `-starter` 後綴，兩者是不同模組。修正後另外只對外開放 Actuator 的 `health` 端點（供 Railway 部署健康檢查與 Uptime 監控），其餘可能洩漏環境變數的端點一律不公開。

### 12. 在功能完全不變的前提下分階段重構

**問題**：系統邊開發邊上線，累積出 1,400 多行的 Service、散落各處的折扣判斷、命名不一致的 API 路徑，以及記錄「哪天改了什麼」的註解。所有功能都是店家實際在用的，重構不能改變任何行為。

**解法**：先補整合測試把現有行為固定下來，再依風險由低到高分批進行，每批一個 PR、CI 通過才合併：
- **拆分職責**：大型 Service 與 Controller 依功能拆分（查詢、報到、通知、結帳預覽、財務報表等），由 ArchUnit 強制「Controller 不碰 Repository」
- **折扣策略化**：首次體驗、回洗優惠、會員折扣抽象成同一介面，由單一計算器逐項擇優
- **效能**：以 Hibernate Statistics 寫成「SQL 條數不隨歷史資料增加」的測試，並依實際查詢條件補上索引
- **API 一致化**：統一錯誤格式（`code` 供前端判斷）、狀態碼語意（201／204／404／403）、路徑命名（複數、`/api/me`、`/api/admin`、以 id 取代帳號）。LINE 內建瀏覽器可能快取舊頁面，所以新舊路徑並存，舊路徑被呼叫時記 log，確認歸零後才移除
- **註解與文件**：變更歷史移到 commit 訊息，重要設計決策整理成架構決策紀錄（`docs/adr/`）

### 13. 並發測試抓到的重複入帳

**問題**：結帳、儲值審核都有「已處理過就擋下」的檢查，但寫法是先讀狀態再寫入。補並發測試時發現，兩位員工同時按「確認入帳」會重複入帳，現場單儲值金結帳連點會重複扣款；舊測試沒抓到，是因為測試會員剛好沒有錢包，同時建立錢包撞到唯一鍵擋下了。

**解法**：有狀態可判斷的操作，先以 `SELECT ... FOR UPDATE` 鎖住該筆、讀回最新狀態再判斷；沒有狀態可判斷的手動儲值與儲值申請，由前端帶請求識別碼（`Idempotency-Key`），寫入有唯一索引的資料表，與操作同一交易，失敗時跟著回滾、可安全重試。拿掉鎖重跑測試確認會失敗，證明測試真的能抓到問題。

## 業務邏輯複雜度（節選）

- **業績認列**嚴格區分「儲值」（預收款）與「結帳完成」（實際業績），兩者不混算
- **折扣互斥**：會員儲值折扣、貓咪 90 天回洗優惠、貓狗首次體驗優惠三者擇優適用，不疊加計算
- **服務項目套餐化**：貓狗價目表依毛長/體型/服務深度拆成數十種組合，並依寵物的體重/品種/毛髮分類自動篩選菜單；狗狗成犬可鎖定固定套餐，不用每次重新依體重篩選
- **假日限定完整套餐**：週六日顧客線上預約僅能選擇完整套餐，不開放單項加購，此限制只影響線上預約，店員現場開單不受影響
- **雙軌庫存扣減**：零售商品在結帳成功時扣庫存，店用耗材則依員工「領用登記」扣庫存，兩者觸發時機與資料模型不同
- **預約備注雙可見性**：內部備注（員工專用）與會員可見備注在 DTO 層隔離，避免內部資訊外洩給顧客
- **員工績效積分**：依接待／結帳分類計算，每個項目可選兩位經手人、積分各半且不可再拆分；「完成」只計次數不計分，並以 Flyway 遷移將歷史積分歸零、重算已結算月份；開單時可先「稍後補填」經手人，集中在待補清單處理
- **會員等級規則**：等級到期日為起算日加一年減一天；過期需重辦，升級或同級續卡重新起算一年，有效期內小額儲值不影響到期日；單筆儲值設最低金額
- **初次預約**：新客線上預約只選時段，由店家到店後現場評估報價，未完成的初次預約不可重複送出
- **代客預約交易一致性**：建立預約與佔用時段名額在同一交易內，任一步驟失敗即退回名額
- **定型化契約**：依主管機關應記載事項修訂（審閱期、儲值金與履約保障、逾時費、個資告知），影像使用改為另行勾選同意，並記錄每位會員簽署的契約版本

## 專案結構

```
src/main/java/com/petgrooming/pet_system/
├── controller/     REST API（顧客端）+ MVC Controller（後台頁面）
├── service/        商業邏輯層（discount/ 為折扣策略）
├── export/         Excel 匯出（財務報表、員工業績、回洗清單）
├── model/          JPA Entity
├── dto/            Request / Response 物件，嚴格區分內外部可見欄位
├── repository/     Spring Data JPA Repository
├── enums/          狀態機、角色、付款方式、折扣類型、會員等級等列舉
├── exception/      分業務例外類別（BusinessException 子類別）
├── interceptor/    JWT 驗證、角色權限、CSRF、觸控裝置導向手機版
├── annotation/     自訂註解（角色權限、登入者注入、略過 CSRF）
├── notification/   LINE 推播整合
├── utils/          共用工具
└── config/         啟動設定、資料回填邏輯

src/main/resources/
├── templates/      Thymeleaf 後台網頁版頁面
├── templates/m/    員工手機版頁面
├── db/migration/   Flyway 種子資料遷移檔案
├── static/liff/    LIFF 顧客端頁面（各自對應獨立 LIFF App，ID 集中於 liff-config.js）
├── static/pwa/     手機版 PWA manifest、Service Worker、圖示
└── static/js/      CSRF token 自動補上、掃碼、美容照片上傳等共用腳本

docs/adr/           架構決策紀錄（悲觀鎖、例外設計、折扣擇優、防重複送出等）
config/             Checkstyle、SpotBugs 設定
```

## 本機啟動

```bash
# 1. 啟動本機 MySQL（Docker）
docker start pet-mysql

# 2. 設定環境變數（資料庫連線、JWT 密鑰、LINE / Cloudinary / Google Calendar 金鑰、Sentry DSN 等）
#    請透過環境變數注入，不寫死於程式碼；Google Calendar 與 Sentry 未設定時會自動停用

# 3. 啟動應用程式
mvn spring-boot:run
```

應用程式預設運行於 `http://localhost:8081`，員工手機版位於 `/m`，健康檢查位於 `/actuator/health`。

API 文件預設關閉；本機開發時設定環境變數 `API_DOCS_ENABLED=true`，登入後可在 `/swagger-ui.html` 瀏覽（正式站不設定，不對外公開）。

```bash
# 測試（需要 Docker，Testcontainers 會自動啟動 MySQL 8）＋靜態分析報告
mvn verify
```
