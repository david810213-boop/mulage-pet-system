# 慕沐村 Mulage pet — 寵物美容店全端管理系統

一套從零開始獨立設計、開發並**實際用於店家日常營運**的寵物美容預約與管理系統。涵蓋顧客端 LINE 預約、店內後台管理、金流儲值、庫存管理、財務報表與員工績效計算，非教學專案或練習作品。

> 開發者：David Hong｜服務業第一線資歷 18 年，自學程式設計後獨力完成本專案

---

## 這是什麼

慕沐村 Mulage pet 解決的是寵物美容店的真實營運痛點：顧客怎麼線上預約、店家怎麼避免同時段超收、金流怎麼安全地儲值扣款、庫存怎麼管理、員工績效怎麼公平拆算、財務報表怎麼即時掌握。系統分成兩端：

- **顧客端**：透過 LINE LIFF 完成登入、預約、查看毛孩美容紀錄、上傳毛孩照片、儲值與查詢消費紀錄，不需額外下載 App。
- **店家後台**：Spring MVC + Thymeleaf 管理介面，涵蓋預約確認、現場開單、會員管理、儲值審核、庫存管理、財務報表、員工績效報表等。

## 技術亮點：工程上實際解決過的問題

### 1. 金流併發扣款的競態條件（Race Condition）
原本的錢包扣款邏輯是「讀取餘額 → 比較 → 寫回」，在高併發情境下會出現超扣風險。改以 `SELECT ... FOR UPDATE` 悲觀鎖重新讀取錢包列後才扣款，確保同一顧客的併發請求會被序列化處理，杜絕餘額被錯誤扣除的情況。

### 2. 同時段預約超收
店家規定同一時段最多接待固定數量寵物，但「還不存在的預約列」沒有東西可以上鎖。設計了獨立的時段容量計數表（`SlotCapacity`），對「時段」本身加悲觀鎖，讓併發預約請求依序處理、即時回報剩餘名額，從根本上避免超賣。

### 3. Hibernate `ddl-auto=update` 的實務限制
專案沒有導入 Flyway，純靠 Hibernate 自動建表。實際踩坑後歸納出一套規範：
- 新增 NOT NULL 欄位必須搭配資料庫層級預設值（`columnDefinition`），因為 Hibernate 無法自動為既有資料列回填
- **MySQL 原生 ENUM 型別欄位，Hibernate 不會自動幫已存在的欄位擴充允許值清單**——Java enum 加新值後直接寫入會拋出 `Data truncated` 例外。修正做法是全面改用 VARCHAR 存列舉值，不依賴資料庫層做列舉約束
- 欄位限制放寬（NOT NULL → nullable）不會自動生效，需要手動下 `ALTER TABLE`

### 4. LINE LIFF 多頁面路由的官方限制
原本假設可以用「單一 LIFF ID + Endpoint URL 路徑轉發」的方式服務多個顧客端頁面，實測後發現行為不一致（部分頁面 404、部分導向錯誤畫面）。查證 LINE 官方文件後確認：LIFF URL 在 LIFF ID 後方附加的路徑，實際上會被包裝進 `liff.state` 查詢參數，瀏覽器只會導向設定好的 Endpoint URL 本身，**並不會真的轉發到不同路徑**。修正為「一個功能頁面對應一組獨立 LIFF App」的官方支援架構，Endpoint URL 直接指向確切頁面，徹底解決路由問題。

### 5. 前端錯誤訊息被靜默吞掉
`fetch()` 呼叫後端 API 時，若後端錯誤回應是純文字而非 JSON，前端寫死用 `res.json()` 解析會拋出例外並被 `.catch()` 接住，導致畫面只顯示寫死的備援錯誤文字，看不到真正的失敗原因。修正為統一後端錯誤回應格式（一律回傳 JSON），前端也改為先讀 `res.text()`、能解析成 JSON 才當 JSON 用，確保錯誤訊息如實呈現，加速除錯。

## 資安事件處理紀錄：憑證外洩的發現與清除

開發過程中發現本機環境變數檔（`.env`，內含資料庫連線資訊）被誤 commit 進版本控制，且已存在於遠端多個分支的歷史紀錄中。處理流程如下，記錄下來作為往後專案的標準作業程序：

1. **定位範圍**：逐一檢查所有分支（`main`／`dev`／`redesign`／`feature/*`）的 commit 歷史與當前工作目錄，確認問題實際影響範圍，而非只看單一分支。
2. **立即止血**：`git rm --cached` 將檔案移出版控追蹤，並補強 `.gitignore` 規則（`.env`、`data/`、`*.db` 等），防止再次被誤加入。
3. **歷史清除**：使用 `git filter-repo` 改寫本機 repo 的完整歷史，移除所有 commit 中曾經包含的機密檔案；並對受影響的每個分支個別執行 `--force` 推送，逐一驗證清除結果。
4. **憑證輪替**：即使歷史已清除，仍將外洩過的資料庫密碼視為已洩漏處理，於雙開發環境同步更換新密碼並驗證連線正常。
5. **事後驗證**：清除完成後，重新從遠端抓取每個分支並逐一確認 `.env`／`data/` 已不存在於任何歷史紀錄或工作目錄中。

> 這起事件也回饋強化了 `.gitignore` 規則與開發習慣：機密設定一律透過環境變數注入（`${VAR_NAME:預設值}` 語法），實際密鑰從一開始就排除在版控之外，`application.yml` 裡看不到任何寫死的機密字串。

## 系統涵蓋的完整業務邏輯

### 預約與現場服務
- 預約狀態機：待確認 → 已確認 → 進行中 → 已完成，含店家最終確認時間；當日臨時預約自動視為已確認並即時推播
- 現場開單（Walk-in）：非預約到店消費，支援純零售訂單（不含美容服務項目時免走「結束服務→核對」流程），員工經手人可事後補填並自動計算績效
- 時段容量管理：單一時段名額調整、單一天公休設定、**固定公休星期**（例如每週固定公休日自動生效，不用逐週手動設定）
- 定型化契約整合：LIFF 與代客預約皆內嵌完整契約條文，電子簽名檔案動態帶入

### 金流與會員
- 會員儲值：僅限轉帳，採「申請 → 店家核帳 → 入帳」兩段式流程，避免顧客端直接竄改餘額；**業績認列嚴格區分「儲值」（預收款）與「結帳完成」（實際業績）**，兩者絕不混算
- 會員分級與升等紅利規則
- 折扣邏輯：會員儲值折扣（依項目類別區分是否適用）與貓咪 90 天回洗優惠**兩套規則互斥、擇優適用**，不疊加計算
- 匯款收款帳戶依用途拆分為「結帳收款」與「儲值金收款（大額專用）」兩組獨立帳戶，各自可設定收款 QR Code
- 匯款付款一律先進入「待對帳」狀態，店家人工核對到帳後才轉為完成，避免收款爭議

### 庫存管理
- 零售商品（賣給顧客）：現場開單可直接加購，結帳成功才真正扣庫存，避免未完成訂單誤扣
- 店用洗劑（店家自用消耗品）：員工「領用登記」扣庫存，逐筆記錄領用人、數量與單價快照；低於安全庫存量自動觸發 LINE 推播通知已綁定的店家/員工

### 財務報表
- 當日／當月營收拆分，並進一步拆分「儲值金扣款」與「非儲值金付款」兩種收款管道
- 業績定義嚴格排除儲值預收款，只認列實際結帳完成的金額
- 成本計算整合庫存資料：零售商品成本（依進貨單價估算）+ 店用洗劑消耗成本（逐筆單價快照，精確計算）
- 支援 Excel 匯出（業績彙總 + 交易明細雙工作表）

### 員工與帳號
- 員工績效積分：依接待／結帳／完成分類計算，支援多人拆分並避免浮點數誤差
- 服務項目管理：名稱／描述／金額可自主修改，項目代碼從型別層級鎖定為唯讀，避免誤改動搖歷史紀錄關聯依據
- 店員可自助綁定個人 LINE 帳號（一次性驗證碼流程），系統通知（如低庫存告警）才能推播到店員手機
- 操作紀錄全面中文化呈現（身分／分類／動作），店家不需要理解英文代碼即可讀懂稽核紀錄
- 預約備注雙可見性：內部備注（員工專用）與會員可見備注嚴格於 DTO 層隔離，避免內部資訊外洩給顧客

### 圖片與內容管理
- 寵物大頭照、美容狀況歷史相簿皆支援雲端圖片上傳（Cloudinary），LIFF 與網頁版後台皆可操作
- 現場開單搜尋寵物時同步顯示照片縮圖，供店員視覺核對，降低同名寵物誤認風險

## LINE LIFF 多頁面架構說明

系統目前有多個獨立的 LIFF 入口頁面，**每個都是各自獨立申請的 LIFF App**（非共用單一 LIFF ID + 路徑轉發，原因見上方技術亮點第 4 點）：

| 功能頁面 | 用途 |
|---|---|
| `index.html` | LIFF 首頁選單 |
| `new-customer.html` | 新客報到導引（填寫個人資料 + 新增毛孩，含進度自動偵測） |
| `bind-line.html` | 店員綁定 LINE 帳號 |
| `booking.html` / `my-appointments.html` / `my-pets.html` / `add-pet.html` / `wallet.html` / `my-profile.html` | 預約、毛孩管理、儲值、個人資料等核心功能 |

新增任何要透過 LINE 開啟的獨立頁面時，務必在 LINE Developers Console 另外申請一組 LIFF App，Endpoint URL 直接指向該頁面，LIFF URL 使用時不接任何路徑。

```
├── controller/     REST API（顧客端）+ MVC Controller（後台頁面）

├── templates/      Thymeleaf 後台頁面
└── static/liff/    LIFF 顧客端頁面（純 HTML/JS，各自對應獨立 LIFF App）
```

## 本機啟動

```bash
# 1. 啟動 MySQL（Docker 容器，對外 port 3307，內部仍是 3306）
docker start pet-mysql

# 2. 設定必要環境變數（DB 連線、JWT_SECRET、LINE / Cloudinary 金鑰等）
#    未設定的第三方服務金鑰（如 Cloudinary）留空即可，對應功能會顯示清楚的錯誤訊息，不影響系統其餘部分啟動

# 3. 啟動應用程式
mvn spring-boot:run

# 4.（選用）若需要外部測試 LINE LIFF，另開終端機執行
ngrok http 8081
```

應用程式預設運行於 `http://localhost:8081`。

⚠️ 本機開發環境須留意：這台機器上除了 Docker 容器的 MySQL（port 3307）外，另外還安裝了原生 MySQL（預設 port 3306），連線資料庫前務必確認 port 是否正確，避免連錯資料庫造成排查混淆。

## 正式環境連線（Railway）

正式環境資料庫與本機開發資料庫完全獨立、不同步。需要連線正式環境資料庫時：

```bash
# 安裝並登入 Railway CLI
npm i -g @railway/cli
railway login

# 連結專案、連進資料庫（走 SSH tunnel，不需開放 Public Networking）
railway link
railway connect MySQL
```
