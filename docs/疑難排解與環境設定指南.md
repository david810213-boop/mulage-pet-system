## 一、雙電腦交替開發：換行符號問題

**症狀**：切換電腦後 `git status` 顯示幾乎所有檔案都是「已修改」，但看不出實際改了什麼。

**原因**：CRLF（Windows）跟 LF（倉庫既有格式）不一致，Git 把每一行都當成「刪除+新增」。

**確認方式**：
```
git diff --stat <某個檔案>
git diff <某個檔案>
```

**清除假性差異**：
```
git checkout -- .
```

**長期建議**：在專案根目錄加 `.gitattributes`，內容 `* text=auto`，兩台電腦都設定 `git config core.autocrlf true`。

## 二、本機 MySQL 有兩個實例，容易連錯

- **原生安裝的 MySQL**：預設 port **3306**
- **Docker 容器 `pet-mysql`**：對外開 port **3307**（容器內部仍是3306）

**App 實際使用的是 Docker 容器（3307）**：
```
mysql -h 127.0.0.1 -P 3307 -u root -p petdb
```

**確認連對地方**：查詢一個最近才新增的表格是否存在（例如 `grooming_item_components`、`pricing_settings`、`cat_breed_coat_mappings`、`flyway_schema_history`），單純查 port 變數不可靠。

## 四、MySQL 原生 ENUM 欄位陷阱

Hibernate `ddl-auto=update` **不會**自動幫已存在的 ENUM 欄位擴充允許值清單，會報 `Data truncated for column 'xxx' at row 1`。

**確認方式**：`SHOW COLUMNS FROM <表名> LIKE '<欄位名>';`，`Type` 顯示 `enum(...)` 且缺少新值就是這個問題。

**修法**：改成 VARCHAR：`ALTER TABLE <表名> MODIFY COLUMN <欄位名> VARCHAR(30) NOT NULL;`

已處理過的欄位：`payment_method`、`source`、`status` 等。**之後新增欄位存列舉值，直接用 VARCHAR，不要讓 Hibernate 自動建成 ENUM。**

## 五、種子資料管理：已改用 Flyway（✅ 架構性解決）

### 陷阱回顧（歷史問題，已解決）

`DataInitializer` 用 `count()==0` 判斷「只在全新資料庫時建立」，正式站資料表早就不是空的，新增的種子資料永遠沒被種進去。這個陷阱至少踩過兩次。

### ✅ 根本解法：Flyway 只管「資料」，schema 仍交給 Hibernate

**關鍵坑：Flyway 預設執行時機在 Hibernate 建表之前**。Spring Boot 預設讓 Flyway 在應用程式啟動最早期執行，早於 `ddl-auto=update` 建表——全新資料庫上會因為表還不存在而直接失敗。

**解法**：`application.yml` 設 `spring.flyway.enabled=false` 關掉內建自動機制，自己寫 `ApplicationRunner`（`DataSeedMigrationRunner`）手動控制在 Hibernate 建完表之後才呼叫 `Flyway.migrate()`。

```yaml
spring:
  flyway:
    enabled: false   # 關掉 Spring Boot 內建的自動啟動機制
    locations: classpath:db/migration
```

**遷移檔案寫法要點**：
- 全部用 `INSERT IGNORE`（靠 UNIQUE 限制防重複），不管全新或既有資料庫都安全
- 涉及外鍵關聯用 `INSERT ... SELECT ... WHERE NOT EXISTS (...)`
- **防呆判斷鍵要下對範圍**：同一批次對同一個父資料連續插入好幾筆子資料時，`WHERE NOT EXISTS` 的判斷條件要精確到「這筆子資料本身」（例如「父ID+分類」），不能只判斷「父資料底下有沒有任何一筆」——後者會導致同批次插入第一筆之後，後面幾筆被誤判成「已經有了」而跳過（這是實際踩過的坑）
- 遷移檔案命名 `V1__xxx.sql`、`V2__xxx.sql`……版本號遞增，`flyway_schema_history` 表記錄執行過的版本，終身只執行一次

**以後新增服務項目種子資料，寫新的 `Vn__xxx.sql` 遷移檔案，不要再回頭改 `DataInitializer.java`**。

**大量資料轉譯的安全做法**：把既有 Java 種子資料轉成 SQL 遷移檔案時，寫腳本從原始碼機械抽取數值（不是手動重打），抽取後核對筆數是否跟原始碼手算的一致，當作基本驗證（這次遷移 91 筆服務項目+156 筆套餐組成都是這樣做，事後也真的抓到一個轉譯過程中自己加進去、原始邏輯沒有的多餘條件，靠核對機制發現並修正）。

**轉譯過程中意外發現的資料一致性問題**：「每次啟動都跑」的校正迴圈如果排除清單漏了某個項目代碼，會導致那個項目的欄位被非預期覆蓋（實際案例：`CAT028` 建立時設定不打折，但折扣校正迴圈的排除清單漏了它，導致每次重啟都被改回可打折，持續發生一段時間才發現）。**這類迴圈的排除清單，新增/修改時要格外小心逐一核對。**

## 六、LINE LIFF 多頁面架構（✅ 已全數完成）

**已確認結論**：LINE 官方**不支援**「單一 LIFF ID + Endpoint URL 路徑轉發」到不同頁面。

**正確做法**：每個要在 LINE 裡開啟的獨立頁面，各自申請一組 LIFF App，Endpoint URL 直接指向那個確切頁面，LIFF URL 使用時**不接任何路徑**。

**9 個頁面全數獨立**：index / new-customer / bind-line / my-profile / add-pet（同一頁靠 `?editPetId=` 判斷新增/編輯模式）/ my-pets / booking / my-appointments / wallet

**申請設定**：Size：Compact，Scopes：`openid`+`profile`，Add friend option：On (Normal)

**其他 LIFF 相關坑**：
1. `liff.login()` 務必帶 `{ redirectUri: window.location.href }`
2. `lineUserId` 資料庫是唯一值，同一支手機的LINE只能綁一個系統帳號
3. 新增給「未登入狀態」呼叫的 `/api/**` 端點，一定要手動加進 `WebConfig` 攔截器白名單

## 七、Thymeleaf 陷阱集錦

### 7.1 inline JavaScript 序列化陷阱

用 `/*[[${變數}]]*/` 塞資料進頁面內的 JS 變數，背後是 Jackson 序列化。**塞整個 JPA entity（尤其含 `LocalDateTime` 欄位）容易序列化失敗，導致整頁渲染中斷、瀏覽器顯示 `ERR_INCOMPLETE_CHUNKED_ENCODING`。**

**修法**：只塞畫面真正需要的欄位，用輕量 Map 或 DTO：
```java
model.addAttribute("retailProducts", retailProductService.listActive().stream()
        .map(p -> java.util.Map.of("id", p.getId(), "name", p.getName(), "price", p.getPrice()))
        .toList());
```

### 7.2 樣板裡的複雜 SpEL 運算式會讓畫面整個截斷

**症狀**：畫面渲染到某個區塊突然停住，後面所有內容（包含按鈕、其他表單欄位）全部消失不見。

**原因**：Thymeleaf 預設是**串流輸出**，樣板運算式如果在渲染中途噴出例外（例如對 `#strings.arraySplit(...)` 產生的陣列做 `.?[...]` 選擇運算子，邊界情況處理不夠穩健），**已經輸出到瀏覽器的部分會保留，後面的內容永遠不會再輸出**——不會顯示錯誤訊息，畫面看起來就像「莫名其妙少了一截」，很難第一時間聯想到是樣板運算式的問題。

**修法**：避免在 Thymeleaf 樣板裡對字串/陣列做複雜的選擇（`.?[...]`）、投影（`.![...]`）運算，改成**在 Controller 先把資料算好成乾淨的 `List<String>` 或 `boolean`，樣板只做最單純的 `list.contains(x)` 判斷**。這種寫法更穩定，出問題時也好除錯（可以直接在 Controller 加中斷點/log 檢查，不用猜樣板引擎在做什麼）。

### 7.3 `onclick` 屬性裡不能用 `[[...]]` 內嵌語法

**症狀**：按鈕點了完全沒反應，沒有任何錯誤訊息或提示。

**原因**：`onclick="unlockPet([[${pet.id}]])"` 這種寫法，**`[[...]]` 這種 Thymeleaf 內嵌表達式語法只有在 `<script th:inline="javascript">` 區塊裡才會被解析**，放在一般 HTML 屬性（`onclick="..."`）裡不會被處理，瀏覽器收到的是字面上壞掉的 JS 語法 `unlockPet([[${pet.id}]])`，點了自然沒反應，瀏覽器 console 通常只會有一個語法錯誤，容易被忽略。

**修法**：一律改用 `th:onclick`：
```html
<button th:onclick="'unlockPet(' + ${pet.id} + ')'">...</button>
```

**排查方式**：如果按鈕點了沒反應，先檢查一下產生出來的 HTML 原始碼（瀏覽器開發者工具「檢查元素」），看 `onclick` 屬性裡的值是不是真的被 Thymeleaf 替換成實際數值，還是原封不動留著 `${...}` 或 `[[...]]` 字樣。

## 八、前端錯誤訊息被吞掉

`fetch()` 呼叫 API，後端錯誤回應如果是純文字（不是 JSON），前端寫死用 `res.json()` 解析會拋例外被 `.catch()` 接住，畫面永遠只顯示同一句寫死的備援錯誤文字。**這個坑至少在三個不同功能上反覆出現過**（2026-08-31 的當天預約限制功能、更早的一次）。

**修法**：
- 後端：API 錯誤一律丟業務例外（`throw new XxxException(ErrorCode.NOT_FOUND, "…")`），由 `GlobalApiExceptionHandler` 統一回傳 `{ status, detail, code, message }`，不在 controller 自己組錯誤回應（見 `docs/adr/0003-business-exception.md`）
- 前端：先讀 `res.text()`，能解析成 JSON 才當 JSON 用，顯示 `message`

**這條規則要當成每次寫新的 `fetch()` 呼叫都要主動套用的習慣，不是專案裡已經有一處修過就代表全部都安全。**

## 九、資安體檢後的修補經驗

### 1. LIFF 頁面存放型 XSS

使用者輸入塞進 `innerHTML` 前，一律先跑過 `escapeHtml()` 函式（每個 LIFF 頁面各自複製一份，沒有共用模組）。純文字顯示優先用 `textContent` 取代 `innerHTML`。

### 2. Cookie 沒有 `SameSite` 屬性

`jakarta.servlet.http.Cookie` 不支援設定，改用 `CookieUtils.buildJwtCookieHeader()` 手動組 `Set-Cookie` 標頭，帶 `SameSite=Lax`。

### 3. 寫死在程式碼裡的預設帳密，repo 又是 Public

啟動時偵測密碼是否還是預設值，是的話印出警告 log。

### 4. CSRF

以 Cookie 登入的 POST／PUT／PATCH／DELETE 由 `CsrfInterceptor` 檢查 token，員工頁面由共用 head 片段載入的 `/js/csrf.js` 自動補上；LIFF（Bearer 登入）不檢查。

尚未處理的資安待辦見《正式上線前準備工作清單》第五節。

### 5. 確認沒問題的部分

SQL Injection（全走 JPA）、IDOR（都用 JWT 解出的 username 查資料）、角色權限（`@RequireRole` 一致）、註冊流程（role 寫死 CUSTOMER）、LINE 登入（有驗證 idToken+aud）、檔案上傳（有檢查 content-type）。

## 十、Maven 依賴管理：版本號要查證，不能憑印象寫

**這個開發沙盒環境連不到 Maven Central**，沒辦法實際跑 `mvn compile` 驗證依賴版本存不存在、彼此相不相容。新增 Google Calendar API 相關依賴時，憑印象寫的版本號（`google-api-services-calendar:v3-rev20240815-2.0.0`）**在 Maven Central 上根本不存在**，本機建置直接失敗。

**正確做法**：新增任何 Maven 依賴，尤其是不常用、版本號有特殊格式的套件（像 Google API 系列常見 `vX-revYYYYMMDD-Z.Y.Z` 這種格式），**先上網搜尋確認 Maven Central 上真實存在的版本號**，不要憑印象或用「合理猜測」的方式編。沙盒無法建置時，push 到 `feature/**` 等分支由 CI 的 `mvn verify` 驗證。

## 十一、Java Unicode 逃逸序列踩坑（⚠️ 教訓成本很高，務必詳讀）

### 背景與三次踩坑

1. **原始符號直接寫進字串**：字元位元組在存檔/複製貼上過程中被弄壞， `javac` 報 `illegal start of expression`  
2. **改用 `\u` 逃逸序列，但註解裡放對照表**：連放在註解裡的實際符號一樣 被弄壞，一樣報錯  
3. **拿掉對照表，但註解文字寫「改用 Java `\u` 逃逸序列」這句話本身**： Java 編譯器不分字串或註解，只要看到反斜線接 `u`，就會嘗試把後面 4 個 字元當十六進位解析，一樣報 `illegal unicode escape`

### 最終正確做法

裝飾符號一律用 `\uXXXX`（或代理對）寫進字串；**註解裡完全不要出現 「反斜線＋u」這兩個字元相連的文字**，也不要放對照用的實際符號；逃逸序列 對照表只放在程式碼以外的地方（README）；`pom.xml` 補上 `project.build.sourceEncoding=UTF-8` 是好習慣但不是萬靈藥。

### 交付前的驗證流程

Claude 交付涉及生僻符號的 Java 程式碼前，會先在沙盒安裝 JDK、用 `javac` 實際編譯過目標檔案，確認沒有這類問題才打包交付。

## 十二、Git 分歧分支合併衝突處理經驗

`git pull` 前先確保本機沒有未 commit 的修改（先 commit，不要隨便 `git stash` 丟掉）。**衝突內容差異很大時（例如同一段文案兩邊各自改了 不同版本），一定要停下來問使用者要保留哪一版，不要自己選**——這是店家 的業務內容決策，不是技術對錯問題。合併完成後，強烈建議立刻重新編譯一次 再 push（衝突標記沒清乾淨，`git status` 不會抓出來，只有實際編譯才抓得到）。

## 十三、其他經驗提醒

- **交付檔案務必給完整內容**，不要只給片段 patch
- **每次改動後先做括號／標籤配對覆查**（腳本數 `{`／`}`、`<div>`／`</div>` 等）
- **交付程式碼前先驗證語法**：Java 用 `javac` 或 CI，JS 用 `node --check`
- **寫程式前先確認 DTO／entity 實際欄位存在**，不要憑印象假設
- **新增到既有資料表的 NOT NULL 欄位，一律搭配 `columnDefinition` 給資料庫層級預設值**
- **新增資料庫欄位／表格不用手動下 SQL**，`ddl-auto=update` 自動處理，列舉欄位用 VARCHAR（第四節）
- **服務項目種子資料一律走 Flyway**，不要回頭改 `DataInitializer.java`（第五節）
- **Thymeleaf 樣板避免複雜 SpEL 運算式**，`onclick` 一律用 `th:onclick`（第七節）
- **push 前跑敏感資訊檢查**：
```powershell
Select-String -Path .\src\main\resources\application.yml -Pattern "cloudinary|CLOUDINARY|api_secret|channel-access-token|ANTHROPIC" -CaseSensitive:$false
```
- **新增 Maven 依賴版本號要先搜尋查證**（第十節）

## 十四、⚠️ N+1 查詢問題 \+ 跨區域延遲排查記錄（2026-09-06/07 新增）

### 背景

店家反映系統（尤其 Dashboard、LIFF 預約頁）載入變得很慢，一度懷疑是 「把 App 部署搬到東南亞、又開啟了 CDN」造成的。

### 排查過程（實際用工具追查，不是憑猜測）

1. **用瀏覽器 Performance API 量測 TTFB**：`performance.getEntriesByType ('navigation')[0].responseStart - requestStart`，Dashboard 頁面量到 **28 秒**，登入頁（幾乎不查資料庫）只要 105ms——證實問題出在 Dashboard 這種要查很多資料的頁面本身，不是全站/網路層級的問題  
2. **查 Railway 即時 log**：光是打開一次 Dashboard，短短十幾秒內跑了 好幾百條 SQL 查詢，且都是同一種模式重複——對每一筆歷史預約各自查一次 服務項目、一次交易紀錄、一次使用者資料，逐筆進行，**這是標準的 N+1 查詢問題**  
3. **查 Railway Metrics**：App/MySQL 的 CPU、Memory 都很健康，沒有資源 卡住的跡象，`Serverless`（休眠）模式也確認是關閉的，排除冷啟動可能  
4. **店家提供關鍵線索**：App 服務曾經從美國搬遷到東南亞（新加坡）節點， 但 MySQL 資料庫留在美國沒有一起搬

### 結論：兩個問題疊加放大，不是單一原因

N+1 查詢問題本來就存在（`AppointmentService.getAllForAdmin()` 這支既有 方法造成的），只是 App 跟資料庫都在美國時，每條查詢延遲只有幾毫秒，幾百 條查詢累加起來也只是零點幾秒，感覺不出來。**App 搬到新加坡後，同樣的 幾百條查詢，每一條都要多繞一次跨太平洋的網路延遲**（來回可能 200~~300ms），原本不明顯的 N+1 問題才被放大到肉眼可見的 20~~30 秒。

**地區搬遷本身不是問題**——新加坡離台灣比美國近，單純搬遷 App 應該讓 「App 本身的處理」變快，問題出在**資料庫沒有跟著搬**。

### 修法方向

1. 短期：確認 App 服務跟資料庫在同一個 Railway 區域（或至少地理位置相近）  
2. 根本：`getAllForAdmin()` 內部組裝回應時改用 Hibernate `@BatchSize` 或 JPQL `JOIN FETCH`，把 N 次個別查詢併成 1\~2 次批次查詢；Dashboard 首頁 不需要撈「全部」歷史預約，改成只查真正需要顯示的少量資料

### 給下次遇到類似狀況的排查步驟

不要一開始就假設是地區/CDN/網路層級問題，**先用瀏覽器 Performance API 分別量測「簡單頁面」跟「複雜頁面」的 TTFB 做對照**，如果只有特定頁面慢、 簡單頁面正常，問題大機率在那個頁面背後的資料庫查詢邏輯，不是全站網路 問題；再查 Railway 即時 log 找實際的 SQL 執行模式，比憑感覺猜測可靠得多。

### 後續（2026-10 已解決）

`getAllForAdmin()` 等後台查詢改用 JPQL `JOIN FETCH` 一次帶出預約、使用者、選擇項目，開單項目與交易紀錄改成批次查詢；首頁與手機版今日頁只查「今天」與「待確認」的預約，會員數改用 COUNT。另寫了 `StaffPageQueryCountTest`：先量一次各頁 SQL 條數，加入一批歷史資料後再量一次，條數不能增加，防止之後改程式又退化回 N+1。網頁版／手機版預約列表、財務報表、現場單列表的查詢條數已固定，但仍會載入全部歷史資料，之後需要時再改成分頁。

## 十五、⚠️ 重複標註導致連鎖編譯錯誤，且單檔驗證方式抓不到（2026-09-07 新增）

### 事故經過

修改 `PetController.java` 的 `getDiscountStatus()` 方法加新參數時，用 `str_replace` 替換的範圍沒有包含原本就存在的 `@GetMapping ("/{petId}/discount-status")` 這一行，導致新舊兩份 `@GetMapping` 疊加在 同一個方法上，變成重複標註。Java 不允許 `@GetMapping` 重複標註（它不是 `@Repeatable` 的 annotation），直接讓整個專案編譯失敗。

### 為什麼一大堆看起來不相關的檔案也一起報錯

編譯失敗的錯誤訊息裡，除了那一行真正的問題，還跑出上百行其他檔案的 `cannot find symbol`（`log` 變數找不到、`builder()` 方法找不到、各種 `getXxx()`/`setXxx()` 找不到）。**這些全部都是這一個錯誤連鎖造成的假象**： 這一個語法錯誤讓 Lombok 的註解處理（`@Slf4j`、`@Builder`、`@Data` 這些 會自動生成程式碼的機制）整個失敗，導致所有依賴 Lombok 生成方法的地方 看起來都「找不到符號」，不是真的有另外幾十個檔案壞掉。

**排查心法**：遇到一大片 `cannot find symbol` 錯誤，先看有沒有**一個** 明確、具體的語法/型別層級錯誤（例如「XXX is not a repeatable annotation type」這種訊息），如果有，優先修那一個，很可能修完之後其他上百行錯誤 就全部消失了，不用逐一去查每一行。

### 為什麼平常的驗證方式沒抓到這個問題

平常驗證 Java 檔案的方式，是把單一檔案丟給 `javac` 單獨編譯（因為連不到 Maven Central，沒辦法帶完整依賴做真正的整合編譯）。**這種方式有一個 盲點**：`@GetMapping` 本身的定義（來自 Spring 框架）在只有單檔、缺依賴 的情況下根本抓不到，編譯器沒辦法真正解析這個 annotation 是不是「可重複 標註」，只會照樣噴一堆「缺依賴」的正常訊息，把這種語意層級的錯誤整個 蓋過去。

### 補強做法

發現這個盲點之後，額外加了一道檢查：**全專案掃描，找有沒有「連續兩行 完全相同的 `@` 開頭標註」**這種可疑模式：

```
for f in glob.glob("src/main/java/**/*.java", recursive=True):
    lines = open(f, encoding="utf-8").read().split("\n")
    for i in range(len(lines) - 1):
        a, b = lines[i].strip(), lines[i+1].strip()
        if a and a == b and a.startswith("@"):
            print(f"{f}:{i+1}  重複: {a}")
```

**根本預防**：`str_replace` 編輯時，`old_str` 的範圍務必包含完整的舊 內容（含上方緊鄰的 annotation/註解），不要只匹配方法簽名本身，避免新舊 內容疊加而不是真正替換。

## 十六、⚠️ 非同步流程改動，只靠語法檢查不夠，要用 jsdom 完整驗證（2026-09-06 新增）

### 事故經過（現場開單頁面會員搜尋功能失效）

在「現場開單建立新單」頁面新增貓咪毛髮分類篩選功能時，`addItemRow()` 函式被改成會讀取 `petSelect`、`currentPetsData` 這兩個變數。但頁面載入時 會**立即同步呼叫一次** `addItemRow()`（讓表單一開始有一行空白項目列）， 而這次呼叫發生在 `petSelect`、`currentPetsData` 這兩個 `const`/`let` 變數宣告**之前**。JavaScript 提前存取還沒宣告的 `const`/`let` 變數會直接 拋出 `ReferenceError`，導致整支 script 從那一行之後全部中斷執行——包括 後面才要註冊的「會員搜尋輸入框監聽器」根本沒機會被設定上去。

**這個問題純語法檢查（`node --check`）完全抓不到**，因為程式碼語法是對的， 只是**執行順序**有問題，是執行期才會出現的錯誤。

### 修法與驗證方式

1. 把變數宣告移到最開始那次 `addItemRow()` 呼叫之前  
2. **用 jsdom（真正的瀏覽器 DOM 引擎，不是簡易假 DOM）實際載入整支 script 並執行過一次**，確認不會在任何一個變數提前存取的地方中斷噴例外：

```javascript
const { JSDOM } = require("jsdom");
const dom = new JSDOM(html, { runScripts: "outside-only" });
global.window = dom.window;
global.document = dom.window.document;
dom.window.eval(scriptSrc);
// 接著模擬使用者操作（選毛孩、選日期等），確認沒有拋出例外
```

3. 需要真的走過 `init()` 完整初始化流程時，要 mock `fetch`（依 URL 回傳 對應假資料）、`liff` 物件（`init`/`isLoggedIn`/`getIDToken`），以及 jsdom 沒有原生支援的 `HTMLCanvasElement.getContext()`（簽名板功能會 用到，補一個假的 context 物件避免打斷初始化流程）

### 這個習慣後續延伸應用

- 修正狗狗鎖定套餐顯示問題時，同樣用 jsdom 走完整初始化流程重現問題、 驗證修正結果，而不是只改程式碼就直接交付  
- 驗證「以預約日期計算優惠資格」邏輯時，模擬三種情境（還沒選日期／選 近期日期／選遠期日期）分別測試，確認每種情境的計算結果都符合預期

**心法**：只要改動涉及「執行順序」「非同步流程」「初始化時機」這類問題， 單純的語法檢查（`javac`/`node --check`）不夠，必須用真正的執行環境 （jsdom）把完整流程跑一次，才能抓到這類問題。

## 十七、⚠️ MySQL 可重複讀下，一般查詢讀到的是舊快照，同時送出的兩筆會漏算（2026-11-15 新增）

### 情境（預約訂金分組計算）

預約訂金以「同一會員同一天」為一組計算（兩位以上才要訂金）。直覺寫法是先鎖住會員那一列，再用一般查詢讀出當天的預約、重算每筆的訂金份額。但同一會員幾乎同時送出兩筆預約時，這樣寫可能兩筆都被算成「當天只有一位、不用訂金」。

### 原因

MySQL InnoDB 預設隔離等級是 **REPEATABLE READ**。一般 `SELECT` 是「快照讀取」，讀的是**交易第一次讀取時**的資料版本。第二筆的交易如果在等鎖之前就已經讀過東西，拿到會員列的鎖之後，一般查詢仍然看不到第一筆剛提交的預約。鎖住了，讀到的卻是舊資料。

### 修法

要改寫份額時，當天的預約改用 `SELECT ... FOR UPDATE`（`AppointmentRepository.lockByUserIdAndDateAndStatusNot`）。加鎖讀取是「當前讀取」，一定讀到最新已提交的版本。順序維持「先鎖會員列、再加鎖讀當天預約」，所有路徑同一順序，避免死結。詳見 `docs/adr/0009-booking-deposit.md`，類似的 Hibernate 快取舊實體問題見 `docs/adr/0002-pessimistic-locking.md`。

**心法**：「先鎖 A、再讀 B 來做判斷」時，B 也要用加鎖讀取，光鎖 A 不保證讀到 B 的最新狀態。

## 十八、⚠️ 部署後 LINE 裡看到的還是舊版頁面（2026-11-15 新增）

### 症狀

後端已經回傳新狀態（例如「待付訂金」），顧客在 LINE 裡打開「我的預約」卻沒有出現匯款資訊卡片。

### 排查順序

1. **先確認改動真的上線了**：Railway 只自動部署 `main`。功能合併進 `redesign` 還沒合併到 `main` 時，正式站跑的是舊版。到 Railway 的 Deployments 看最新一次部署的 commit
2. **再看是不是快取**：LIFF 頁面是靜態 HTML，Spring 預設不送 `Cache-Control`，LINE 內建瀏覽器會依 `Last-Modified` 自行推估快取時間，新版部署後還是顯示舊頁面

### 修法

`WebConfig` 對 `/liff/*` 加一個 Filter 回傳 `Cache-Control: no-cache`，瀏覽器每次都先向伺服器確認，沒有變動時回 304，不用重新下載。共用的 CSS／JS 改版時，仍在引用處加版本號（例如 `liff-theme.css?v=3`），確保舊快取一定失效。

## 十九、分支名稱不在清單內，push 後 CI 不會跑（2026-11-15 新增）

`.github/workflows/ci.yml` 只在 push 到 `main`、`redesign`、`refactor/**`、`feature/**`、`perf/**` 時執行。曾經開了 `fix/liff-no-cache` 分支，push 後 Checks 頁什麼都沒有，以為 CI 壞了，其實是分支名稱不在清單內。修正類的改動也用 `feature/` 開頭，或先在 `ci.yml` 加上新的前綴。開 PR 到 `main`／`redesign` 時也會觸發，但只看 push 的話要注意這點。

## 二十、⚠️ 測試單獨跑會過、整批跑會失敗（2026-11-15 新增）

整合測試共用同一個 Testcontainers MySQL，資料不會在每支測試之間清空，曾經踩過三種情況：

1. **測試資料的時段不在營業時間內**：訂金流程測試用了 10:00 的時段，店家 11:00 才開門，預約被擋下。測試資料要用營業時間內的時段（例如 12:00）
2. **挑到公休日**：時段管理冒煙測試用固定推算的日期，剛好碰到公休日就失敗。改成在測試裡找一個確定開店的未來日期
3. **查詢條數受先跑的測試影響**：`StaffPageQueryCountTest` 的條數會隨資料庫裡已有的資料（別支測試留下的顧客、預約）和第一次載入頁面的額外查詢而不同。改成先自己建立足夠的顧客與歷史資料，並先預熱一次再量測

**心法**：測試不要依賴「資料庫目前剛好是什麼狀態」，需要的前提條件自己建立；只在 CI 失敗、本機單獨跑會過時，先懷疑執行順序。
