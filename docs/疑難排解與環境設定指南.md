## 一、雙電腦交替開發：換行符號問題

症狀：切換電腦後 `git status` 顯示幾乎所有檔案都是「已修改」。原因：CRLF （Windows）跟 LF 不一致。確認：`git diff --stat <檔案>`。清除：`git checkout -- .`。 長期建議：加 `.gitattributes`（`* text=auto`），兩台電腦都設定 `git config core.autocrlf true`。

## 二、本機 MySQL 有兩個實例，容易連錯

原生安裝 port 3306，Docker 容器 `pet-mysql` 對外開 port 3307。App 實際用 3307：`mysql -h 127.0.0.1 -P 3307 -u root -p petdb`。

## 三、正式環境（Railway）資料庫連線

`railway link` → `railway connect MySQL`（走 SSH tunnel，不用開 Public Networking）。公司電腦連不了（防火牆擋 SSH tunnel），只能等回本機電腦。

## 四、MySQL 原生 ENUM 欄位陷阱

`ddl-auto=update` 不會自動幫已存在的 ENUM 欄位擴充允許值，改用 VARCHAR。

## 五、種子資料管理：已改用 Flyway（✅ 架構性解決）

`spring.flyway.enabled=false` 關掉內建自動機制，自己寫 `DataSeedMigrationRunner` 手動控制在 Hibernate 建表之後才呼叫 `Flyway.migrate()`。遷移檔案全部用 `INSERT IGNORE`，涉及外鍵關聯用 `INSERT ... SELECT ... WHERE NOT EXISTS (...)`。

## 六、LINE LIFF 多頁面架構（✅ 已全數完成）

9 個頁面全數獨立申請 LIFF App，不支援路徑轉發。

## 七、Thymeleaf 陷阱集錦

7.1 inline JavaScript 序列化陷阱（塞整個 entity 容易序列化失敗）； 7.2 樣板裡複雜 SpEL 運算式會讓畫面整個截斷（改成後端先算好乾淨的 List）； 7.3 `onclick` 屬性裡不能用 `[[...]]` 內嵌語法，要用 `th:onclick`。

## 八、前端錯誤訊息被吞掉

`fetch()` 呼叫 API，後端錯誤回應如果是純文字，前端用 `res.json()` 解析 會拋例外被 `.catch()` 接住。**這個坑至少在三個不同功能上反覆出現過** （2026-08-31 的當天預約限制功能、更早的一次），修法一律是先讀 `res.text()`， 能解析成 JSON 才當 JSON 用。**這條規則要當成每次寫新的 `fetch()` 呼叫都要 主動套用的習慣，不是專案裡已經有一處修過就代表全部都安全。**

## 九、資安體檢後的修補經驗

LIFF 頁面存放型 XSS（`escapeHtml()`）、Cookie 缺少 `SameSite`（手動組 `Set-Cookie` 標頭）、原始碼內建預設密碼且倉庫公開（啟動時偵測並印警告）。 尚未處理的資安待辦見《正式上線前準備工作清單》第五節。

## 十、Maven 依賴管理：版本號要查證，不能憑印象寫

這個沙盒環境連不到 Maven Central，新增依賴前要先上網搜尋確認版本號真實 存在，不要憑印象猜。

## 十一、Java Unicode 逃逸序列踩坑（⚠️ 教訓成本很高，務必詳讀）

### 背景與三次踩坑

1. **原始符號直接寫進字串**：字元位元組在存檔/複製貼上過程中被弄壞， `javac` 報 `illegal start of expression`  
2. **改用 `\u` 逃逸序列，但註解裡放對照表**：連放在註解裡的實際符號一樣 被弄壞，一樣報錯  
3. **拿掉對照表，但註解文字寫「改用 Java `\u` 逃逸序列」這句話本身**： Java 編譯器不分字串或註解，只要看到反斜線接 `u`，就會嘗試把後面 4 個 字元當十六進位解析，一樣報 `illegal unicode escape`

### 最終正確做法

裝飾符號一律用 `\uXXXX`（或代理對）寫進字串；**註解裡完全不要出現 「反斜線＋u」這兩個字元相連的文字**，也不要放對照用的實際符號；逃逸序列 對照表只放在程式碼以外的地方（README）；`pom.xml` 補上 `project.build.sourceEncoding=UTF-8` 是好習慣但不是萬靈藥。

### 交付前的驗證流程

Claude 交付涉及生僻符號的 Java 程式碼前，會先在沙盒安裝 JDK、用 `javac` 實際編譯過目標檔案，確認沒有這類問題才打包交付。

## 十二、Git 分歧分支合併衝突處理經驗

`git pull` 前先確保本機沒有未 commit 的修改（先 commit，不要隨便 `git stash` 丟掉）。**衝突內容差異很大時（例如同一段文案兩邊各自改了 不同版本），一定要停下來問使用者要保留哪一版，不要自己選**——這是店家 的業務內容決策，不是技術對錯問題。合併完成後，強烈建議立刻重新編譯一次 再 push（衝突標記沒清乾淨，`git status` 不會抓出來，只有實際編譯才抓得到）。

## 十三、其他經驗提醒

交付檔案務必給完整內容；每次改動後做括號/標籤配對覆查；交付程式碼前先在 沙盒用 `javac`/`node --check` 驗證過語法；push 前跑敏感資訊檢查；新增 Maven 依賴版本號要先搜尋查證。

## 十四、⚠️ N+1 查詢問題 \+ 跨區域延遲排查記錄（2026-09-06/07 新增）

### 背景

店家反映系統（尤其 Dashboard、LIFF 預約頁）載入變得很慢，一度懷疑是 「把 App 部署搬到東南亞、又開啟了 CDN」造成的。

### 排查過程（實際用工具追查，不是憑猜測）

1. **用瀏覽器 Performance API 量測 TTFB**：`performance.getEntriesByType ('navigation')[0].responseStart - requestStart`，Dashboard 頁面量到 **28 秒**，登入頁（幾乎不查資料庫）只要 105ms——證實問題出在 Dashboard 這種要查很多資料的頁面本身，不是全站/網路層級的問題  
2. **查 Railway 即時 log**：光是打開一次 Dashboard，短短十幾秒內跑了 好幾百條 SQL 查詢，且都是同一種模式重複——對每一筆歷史預約各自查一次 服務項目、一次交易紀錄、一次使用者資料，逐筆進行，**這是標準的 N+1 查詢問題**  
3. **查 Railway Metrics**：App/MySQL 的 CPU、Memory 都很健康，沒有資源 卡住的跡象，`Serverless`（休眠）模式也確認是關閉的，排除冷啟動可能  
4. **店家提供關鍵線索**：App 服務曾經從美國搬遷到東南亞（新加坡）節點， 但 MySQL 資料庫留在美國沒有一起搬

### 結論：兩個問題疊加放大，不是單一原因

N+1 查詢問題本來就存在（`AppointmentService.getAllForAdmin()` 這支既有 方法造成的），只是 App 跟資料庫都在美國時，每條查詢延遲只有幾毫秒，幾百 條查詢累加起來也只是零點幾秒，感覺不出來。**App 搬到新加坡後，同樣的 幾百條查詢，每一條都要多繞一次跨太平洋的網路延遲**（來回可能 200~~300ms），原本不明顯的 N+1 問題才被放大到肉眼可見的 20~~30 秒。

**地區搬遷本身不是問題**——新加坡離台灣比美國近，單純搬遷 App 應該讓 「App 本身的處理」變快，問題出在**資料庫沒有跟著搬**。

### 修法方向

1. 短期：確認 App 服務跟資料庫在同一個 Railway 區域（或至少地理位置相近）  
2. 根本：`getAllForAdmin()` 內部組裝回應時改用 Hibernate `@BatchSize` 或 JPQL `JOIN FETCH`，把 N 次個別查詢併成 1\~2 次批次查詢；Dashboard 首頁 不需要撈「全部」歷史預約，改成只查真正需要顯示的少量資料

### 給下次遇到類似狀況的排查步驟

不要一開始就假設是地區/CDN/網路層級問題，**先用瀏覽器 Performance API 分別量測「簡單頁面」跟「複雜頁面」的 TTFB 做對照**，如果只有特定頁面慢、 簡單頁面正常，問題大機率在那個頁面背後的資料庫查詢邏輯，不是全站網路 問題；再查 Railway 即時 log 找實際的 SQL 執行模式，比憑感覺猜測可靠得多。

## 十五、⚠️ 重複標註導致連鎖編譯錯誤，且單檔驗證方式抓不到（2026-09-07 新增）

### 事故經過

修改 `PetController.java` 的 `getDiscountStatus()` 方法加新參數時，用 `str_replace` 替換的範圍沒有包含原本就存在的 `@GetMapping ("/{petId}/discount-status")` 這一行，導致新舊兩份 `@GetMapping` 疊加在 同一個方法上，變成重複標註。Java 不允許 `@GetMapping` 重複標註（它不是 `@Repeatable` 的 annotation），直接讓整個專案編譯失敗。

### 為什麼一大堆看起來不相關的檔案也一起報錯

編譯失敗的錯誤訊息裡，除了那一行真正的問題，還跑出上百行其他檔案的 `cannot find symbol`（`log` 變數找不到、`builder()` 方法找不到、各種 `getXxx()`/`setXxx()` 找不到）。**這些全部都是這一個錯誤連鎖造成的假象**： 這一個語法錯誤讓 Lombok 的註解處理（`@Slf4j`、`@Builder`、`@Data` 這些 會自動生成程式碼的機制）整個失敗，導致所有依賴 Lombok 生成方法的地方 看起來都「找不到符號」，不是真的有另外幾十個檔案壞掉。

**排查心法**：遇到一大片 `cannot find symbol` 錯誤，先看有沒有**一個** 明確、具體的語法/型別層級錯誤（例如「XXX is not a repeatable annotation type」這種訊息），如果有，優先修那一個，很可能修完之後其他上百行錯誤 就全部消失了，不用逐一去查每一行。

### 為什麼平常的驗證方式沒抓到這個問題

平常驗證 Java 檔案的方式，是把單一檔案丟給 `javac` 單獨編譯（因為連不到 Maven Central，沒辦法帶完整依賴做真正的整合編譯）。**這種方式有一個 盲點**：`@GetMapping` 本身的定義（來自 Spring 框架）在只有單檔、缺依賴 的情況下根本抓不到，編譯器沒辦法真正解析這個 annotation 是不是「可重複 標註」，只會照樣噴一堆「缺依賴」的正常訊息，把這種語意層級的錯誤整個 蓋過去。

### 補強做法

發現這個盲點之後，額外加了一道檢查：**全專案掃描，找有沒有「連續兩行 完全相同的 `@` 開頭標註」**這種可疑模式：

```
for f in glob.glob("src/main/java/**/*.java", recursive=True):
    lines = open(f, encoding="utf-8").read().split("\n")
    for i in range(len(lines) - 1):
        a, b = lines[i].strip(), lines[i+1].strip()
        if a and a == b and a.startswith("@"):
            print(f"{f}:{i+1}  重複: {a}")
```

**根本預防**：`str_replace` 編輯時，`old_str` 的範圍務必包含完整的舊 內容（含上方緊鄰的 annotation/註解），不要只匹配方法簽名本身，避免新舊 內容疊加而不是真正替換。

## 十六、⚠️ 非同步流程改動，只靠語法檢查不夠，要用 jsdom 完整驗證（2026-09-06 新增）

### 事故經過（現場開單頁面會員搜尋功能失效）

在「現場開單建立新單」頁面新增貓咪毛髮分類篩選功能時，`addItemRow()` 函式被改成會讀取 `petSelect`、`currentPetsData` 這兩個變數。但頁面載入時 會**立即同步呼叫一次** `addItemRow()`（讓表單一開始有一行空白項目列）， 而這次呼叫發生在 `petSelect`、`currentPetsData` 這兩個 `const`/`let` 變數宣告**之前**。JavaScript 提前存取還沒宣告的 `const`/`let` 變數會直接 拋出 `ReferenceError`，導致整支 script 從那一行之後全部中斷執行——包括 後面才要註冊的「會員搜尋輸入框監聽器」根本沒機會被設定上去。

**這個問題純語法檢查（`node --check`）完全抓不到**，因為程式碼語法是對的， 只是**執行順序**有問題，是執行期才會出現的錯誤。

### 修法與驗證方式

1. 把變數宣告移到最開始那次 `addItemRow()` 呼叫之前  
2. **用 jsdom（真正的瀏覽器 DOM 引擎，不是簡易假 DOM）實際載入整支 script 並執行過一次**，確認不會在任何一個變數提前存取的地方中斷噴例外：

```javascript
const { JSDOM } = require("jsdom");
const dom = new JSDOM(html, { runScripts: "outside-only" });
global.window = dom.window;
global.document = dom.window.document;
dom.window.eval(scriptSrc);
// 接著模擬使用者操作（選毛孩、選日期等），確認沒有拋出例外
```

3. 需要真的走過 `init()` 完整初始化流程時，要 mock `fetch`（依 URL 回傳 對應假資料）、`liff` 物件（`init`/`isLoggedIn`/`getIDToken`），以及 jsdom 沒有原生支援的 `HTMLCanvasElement.getContext()`（簽名板功能會 用到，補一個假的 context 物件避免打斷初始化流程）

### 這個習慣後續延伸應用

- 修正狗狗鎖定套餐顯示問題時，同樣用 jsdom 走完整初始化流程重現問題、 驗證修正結果，而不是只改程式碼就直接交付  
- 驗證「以預約日期計算優惠資格」邏輯時，模擬三種情境（還沒選日期／選 近期日期／選遠期日期）分別測試，確認每種情境的計算結果都符合預期

**心法**：只要改動涉及「執行順序」「非同步流程」「初始化時機」這類問題， 單純的語法檢查（`javac`/`node --check`）不夠，必須用真正的執行環境 （jsdom）把完整流程跑一次，才能抓到這類問題。
