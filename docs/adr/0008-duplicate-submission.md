# 0008 金流操作防重複送出：狀態列加鎖＋請求識別碼

## 背景
結帳、確認收款、退款、儲值審核、手動儲值、儲值申請都是「按一次就動到錢」的操作。連點、網路重送、或兩位員工同時操作同一筆時，原本「先讀狀態再寫入」的檢查在兩個請求同時讀到「未處理」時擋不住，實測會重複入帳（儲值申請同時確認、確認與駁回同時發生）與重複扣款（現場單儲值金結帳）。

## 決策
- **有狀態可判斷的操作**（預約與現場單的結帳／確認匯款／退款、儲值申請的確認／駁回）：先以 `SELECT ... FOR UPDATE` 鎖住該筆並讀回狀態欄位（`AppointmentRepository.lockPaidById`、`WalkInOrderRepository.lockPaidById`、`TopUpRequestRepository.lockStatusById`），再依讀回的值判斷能否繼續。同一筆的操作依序執行，後到的請求看到的是前一個已提交的結果。
  - 只讀回判斷用的欄位、用原生查詢：鎖定讀取一定讀到最新已提交的值；若改成鎖定查詢整個實體，快取中已有同一實體時 Hibernate 會回傳舊值（原因同 0002）。不用 detach 實體，是因為網頁版 controller 可能還持有同一個實體，detach 後延遲載入會失敗。
  - 鎖的順序固定為「單據 → 錢包」，與既有錢包鎖一致，不會互相等待造成死結。
- **沒有狀態可判斷的操作**（店家手動儲值、顧客送出儲值申請，每次送出都是新的一筆）：前端每份表單產生一個識別碼（API 用 `Idempotency-Key` 標頭，網頁表單用隱藏欄位 `idempotencyKey`），`IdempotencyService.claim` 把它寫進有唯一索引的 `idempotency_keys` 表，與本次操作同一個交易。
  - 操作失敗時識別碼跟著回滾，可用同一個識別碼重試；成功後再送出同一個識別碼回 409 `CONFLICT`。
  - 沒帶識別碼（舊版快取頁面、其他呼叫端）時不檢查，行為與原本相同。
  - 網頁版手動儲值遇到重複送出時顯示「已完成，未重複入帳」而不是錯誤：連點時瀏覽器只顯示最後一次的回應，前一次其實已成功。
  - 識別碼保留 7 天後由排程清除。

## 後果
- `DuplicateSubmissionTest` 以並發測試驗證每種操作只成功一次；拿掉鎖時其中 3 項會失敗（重複入帳、重複扣款）。
- 新增會動到錢的操作時：有狀態欄位的先呼叫對應的 lock 方法讀狀態；沒有狀態欄位的讓前端帶識別碼並呼叫 `IdempotencyService.claim`。
