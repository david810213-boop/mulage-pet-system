## 四、 系統穩定度與部署維護 (Reliability & Scalability)

| 項目 | 說明與操作步驟 | 負責人 | 狀態 |
| :---- | :---- | :---- | :---- |
| **設定健康檢查路徑 (Healthcheck Path)** | 在 Railway 部署設定中指定 API 健康檢查路徑（如 `/actuator/health` 或 `/api/health`），確保部署時實現無縫平滑更新 (Zero-downtime deployment)。 | DevOps / 後端 | ⏹ 待處理 |
| **關閉無伺服器休眠 (Serverless/Sleep)** | 確認 Railway 部署設定中的「啟用無伺服器 (Serverless)」處於關閉狀態，維持容器常駐，避免顧客造訪時觸發容器冷啟動 (Cold Start) 造成載入延遲。 | DevOps | ✅ 已確認關閉 |
| **確認重啟策略 (Restart Policy)** | 確認服務的重啟策略設定為 **On Failure (失敗時重啟)**，並將最大重試次數設為適當數值（預設 10 次），保障服務崩潰時能自動恢復。 | DevOps | ⏹ 待處理 |
| **⚠️ N+1 查詢優化**（2026-09-07 新增，**仍待處理**） | **實測發現**：Dashboard 首頁跟部分後台列表頁（呼叫 `AppointmentService.getAllForAdmin()` 的地方）會對每一筆歷史預約各自觸發多次額外查詢（查交易紀錄、查服務項目、查使用者資料，逐筆進行，沒有用 `JOIN`/批次查詢合併），隨著測試資料累積，單次頁面載入可能觸發幾百條 SQL。**這個問題本身還沒解決**，只是資料庫遷回同區域後，每條查詢延遲變小，症狀暫時不明顯了。建議上線前排時間處理：① 短期治標——Dashboard 首頁改成只查「今天」「待確認」等真正需要顯示的少量資料，不要撈全部歷史紀錄；② 根本解法——`getAllForAdmin()` 內部組裝回應時改用 Hibernate `@BatchSize` 或 JPQL `JOIN FETCH`，把 N 次個別查詢併成 1\~2 次批次查詢。 | 後端工程師 | ⏹ 待處理 |
